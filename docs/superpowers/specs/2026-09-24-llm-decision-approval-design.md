# S1-S5 LLM 决策与审批模型

- 日期：2026-09-24
- 状态：已获用户批准的设计
- 范围：S1 发现/补全、S2 Mail1、S3 回复运营、S4 活跃素材、S5 OCR/匹配/QC

## 1. 目标

Rockbase 要支持两种完整运行方式：

1. **审批模式（默认）**：每个阶段完成确定性预处理、LLM 语义处理和确定性校验后，生成可审阅的阶段产物，暂停等待 Console 决策。
2. **全自动模式**：用户启动 run 时预先批准本次 run 的非禁区阶段，阶段按同一套 LLM、校验和审计逻辑继续运行，不逐卡等待。

用户的角色是业务决策者，不是数据处理执行者。用户不能代替系统筛选候选人、撰写邮件、判断回复意图、整理资料或执行匹配；这些工作由确定性代码和 LLM 完成。用户只能批准、不批准，并可在不批准时附带意见。

## 2. 非目标

- 不让 LLM 选择收件人、发送目标、模板代码、opt-out 结果、发送开关或审批结果。
- 不让用户直接编辑候选列表、邮件正文、回复意图、字段值或 OCR 结果。
- 不以全自动模式绕过真实发信、生产主表写回或 opt-out 等安全边界。
- 不把 JSON 语法修复、线程匹配、去重、限速、日期计算、CSV 序列化等确定性工作交给 LLM。

## 3. 运行模式

### 3.1 审批模式

启动 run 时写入 `mode=review`。每个需要决策的阶段产物都创建一张审批卡片并暂停该阶段，直到 Console 提交决策。run state 保存模式、策略版本、阶段状态和当前产物版本。

### 3.2 全自动模式

启动 run 时写入 `mode=auto`，同时记录操作者、时间、策略版本和授权范围。非禁区阶段可以按策略自动通过，但仍必须生成阶段产物、校验结果和审计记录。run 启动后不能切换模式；需要改变模式时停止当前 run 并创建新 run。

全自动模式不是跳过 LLM、校验或审计，而是把用户对非禁区阶段的批准前移到 run 启动时。

## 4. 审批协议

### 4.1 Console 是唯一审批写入口

批准、不批准和反馈意见只通过 Console API 提交。CLI 和 approval 文件可以运行、查看和导出状态，但不能形成审批决策。每个决策必须绑定：

- `run_id`
- `stage_id`
- `artifact_id`
- `artifact_version`
- `decision_id`
- 操作者身份
- 决策时间
- 决策动作
- 产物内容哈希
- 可选反馈意见

服务端必须拒绝对过期 artifact version 的决策，避免用户批准的内容与实际执行内容不一致。

### 4.2 决策动作

| 动作 | 语义 | 结果 |
|---|---|---|
| `approve` | 批准当前阶段产物 | 进入下一阶段或执行待批的阶段动作 |
| `reject` | 不批准当前阶段产物 | 阶段不前进，标记为需重新生成 |
| `reject_with_feedback` | 不批准并给出意见 | 意见作为下一轮 LLM 的约束，生成新版本并重新出卡 |
| `approve_run` | 启动时批准本 run 的非禁区阶段 | 等价于全自动模式，不适用于永久安全禁区 |

用户不能通过审批 API 修改产物字段。`reject_with_feedback` 的意见是给 LLM 的约束数据，不是用户对结果的直接替代。

### 4.3 审批卡片

每张卡片固定展示：

1. 系统做了什么：输入范围、处理数量、跳过和失败数量。
2. LLM 判断：结构化结果、置信度、简短理由。
3. 确定性校验：通过、失败和人工复核项。
4. 证据：脱敏且有界的摘要、来源行或附件引用。
5. 待批动作：将要写入、生成或进入下一阶段的具体动作。
6. 决策控件：批准、不批准、带意见打回。

LLM 结果、证据和校验结果均为只读。原始邮件正文、凭据和完整生产数据不得进入事件、日志或普通卡片摘要。

## 5. S1-S5 语义边界

### S1：发现与补全

**LLM 负责**：自然语言需求理解、候选相关性、真人/机构/媒体判断、模糊资料归纳和理由说明。

**确定性代码负责**：API 请求、分页、字段解析、平台 ID、邮箱/URL 校验、去重、行映射、硬过滤、排序约束、文件写入和备份。

**审批产物**：候选清单、每项的 LLM 理由和置信度、确定性过滤结果、待写入的候选集合。

**当前差距**：YouTube 的实体筛选已有代表性 LLM 路径；Instagram、TikTok、X 的模糊发现尚未统一接入完整编排。主页事实补全不需要 LLM，直接 API 或浏览器提取即可。

### S2：Mail1 草稿与外联

**LLM 负责**：根据已批准的候选资料生成个性化 Mail1、选择合适的语气和上下文表达、说明生成理由。

**确定性代码负责**：收件人和字段绑定、模板约束、敏感内容检查、首封链接守卫、限速、幂等、发送策略和 SMTP 执行。

**审批产物**：每封草稿的正文、输入证据、生成理由、质量校验和待入队动作。

**当前差距**：YouTube Mail1 已接入 full runner；其他平台仍未统一接入。草稿生成属于必须使用 LLM 的语义工作；真实发送永远不因 LLM 结果自动发生。

### S3：回复运营

**LLM 负责**：回复意图、报价和条件提取、摘要、下一步建议、需要语义判断的语言理解、Mail2/Mail3 草稿生成。

**确定性代码负责**：MIME 解析、线程归属、`In-Reply-To`/`References` 匹配、external ID 去重、opt-out、状态机、模板代码映射、限速、审批和发送。

**审批产物**：意图、报价条件、摘要、下一步建议、证据引用和拟生成草稿。

**当前差距**：事件接收、幂等 worker、同步基础已完成；意图分类有未提交实现；语义摘要/条件/下一步建议尚未完成。`master_sync.summary_of` 的有界预览只能作为 LLM 不可用时的人工复核 fallback。

### S4：活跃素材

**LLM 负责**：简介语义整理、账号类型判断、活跃度证据解释、标签建议和跨语言含义整理。

**确定性代码负责**：数值和时间计算、来源证据保存、标签 allow-list、字段格式化、去重、备份和写回。

**审批产物**：建议字段、标签、证据、模型理由、置信度和待写回差异。

**当前差距**：现有 apply 脚本能够消费外部生成的 JSONL 并确定性写回，但生成调用尚未纳入统一运行链；需要将 LLM 生成、校验、审批和 apply 串成一个阶段。

### S5：OCR、Brief 匹配与交付检查

**LLM 负责**：复杂截图视觉结构、多语言和图表语义、Brief 与 Master 的语义匹配、模糊候选解释。

**确定性代码负责**：OCR 后处理、邮箱/handle 正则、国家归一化、百分比校验、sha1/dhash 去重、硬匹配、交付字段检查、写回和备份。

**审批产物**：OCR/匹配结果、候选解释、置信度、冲突和待写回差异。

**当前差距**：OCR 已有 Vision → 多模态 LLM → tesseract 的服务端安全选择，且后处理保持确定性；Brief 匹配和交付检查尚未成为统一阶段。

## 6. 永久安全边界

以下动作在审批模式和全自动模式下都不能仅凭 `approve_run` 自动执行：

1. `mailkit.send --execute` 真实发送邮件。
2. `master_sync --execute` 写入生产 master CSV。
3. 任何 opt-out 地址进入发送队列；opt-out 是确定性硬拒绝，不接受模型或用户豁免。
4. 未通过确定性 schema、策略、敏感内容和权限校验的产物进入下一阶段。

上述动作必须产生独立审批卡片和独立审计记录。写回动作执行前必须备份，失败时保留可重试状态，不得伪装为成功。

## 7. LLM 失败与重新生成

- 模型超时、不可用、返回非法 schema 或低于置信度阈值时，阶段进入 `manual_review`，不得静默通过。
- 语法类错误使用本地 JSON 解析和有界修复；不为尾逗号、代码围栏或外围说明发起第二次模型调用。
- 语义失败可以在有限重试预算内重新调用模型；超过预算后进入人工复核。
- 用户反馈必须保留为版本化输入，旧产物、提示约束、模型版本和校验结果都进入审计；不得覆盖历史版本。

## 8. 审计与可恢复性

每个阶段记录输入摘要哈希、模型/提示版本、输出 schema、确定性校验结果、artifact 版本、决策和执行结果。日志只包含 run/stage/artifact/decision ID 及脱敏诊断，不包含完整邮件正文、凭据或生产数据。

阶段失败时可以从最后一个已批准且校验通过的 artifact 恢复。重复事件和重复审批必须幂等；过期审批、错误操作者或哈希不一致必须拒绝。

## 9. 成功标准

- 每个 S1-S5 阶段都有明确的 LLM/确定性职责表和结构化阶段产物。
- 审批模式可以在每个阶段暂停，Console 可以批准、拒绝或带意见打回；用户不能直接编辑业务产物。
- 全自动模式可以在 run 启动时预批准非禁区阶段，并保留与逐阶段审批相同的产物、校验和审计记录。
- 真实发送、生产 master 写回和 opt-out 硬拒绝不被全自动模式绕过。
- 意见打回会生成新 artifact 版本，旧版本可追溯，LLM 负责重新生成而不是用户手工代替执行。
- 确定性工作不调用 LLM；必须依赖语义理解或视觉理解的工作有 LLM 路径和人工复核 fallback。
- 所有新阶段通过离线契约测试验证；真实账号验收仍由部署方使用测试账号完成。
