# 🛰️ [Process] S1 KOL Enrichment SOP

> **本工作流基于 `s1-inbox-enrichment` 技能，专门服务现有 `S1 Inbox` 主表的资料补齐，不负责 Raw 建表、不负责 S2 迁移。**

## 一、 核心目标 (Objective)

对已经存在的 `S1 Inbox` 表执行纯 `S1` 资料补齐。

本工作流只做三类事情：

- 补平台原始事实
- 补基础联系方式线索
- 补可用于进入 `S2` 判断的基础字段

本工作流不做：

- Raw 表映射生成 S1
- S1 -> S2 迁移
- 商业定位提炼
- 客户友好包装
- 邮件/DM 执行字段生成

## 二、 执行步骤 (Run Steps)

### Step 1. 分析要处理的表格

执行本工作流前，必须先明确本轮要处理的目标表格。

若用户已经给出表格路径，则以该表格为准。

若用户没有给出表格路径，必须先向用户确认：

- 本轮要处理哪一张 `S1 Inbox` 表
- 是否处理全表，还是只处理指定分区 / 平台 / 行号范围

在表格未确认前，不进入后续步骤。

本步骤至少要完成以下检查：

1. 目标表是否存在
2. 是否为 `S1` 表而不是 `Raw` 或 `S2` 表
3. 当前表头是否能识别出关键字段
4. 是否需要先备份

### Step 2. 分析字段缺口，并给出执行方案

确认表格后，第二步不是直接跑脚本，而是先做字段分析。

字段分析至少要回答 3 件事：

1. 当前这张表缺失了哪些 `S1` 字段
2. 这些字段里，哪些适合用 `API / EasyKOL` 补
3. 这些字段里，哪些适合用现有 `scripts/` 补

输出时必须给用户两部分内容：

- 字段缺失分析
- 执行方案

在用户确认执行方案前，不进入正式执行。

#### 2.1 字段缺失分析

字段缺失分析建议至少覆盖以下字段：

- `账号ID`
- `频道/作者名称`
- `平台`
- `账号链接`
- `语言`
- `博主国家`
- `粉丝数`
- `账号类目标签__平台抓取`
- `账号简介__平台抓取`
- `外链__平台抓取`
- `近期10条均播`
- `置顶最高单条播放量 / 置顶最高播放`
- `联系方式`
- `联系方式备注`

分析输出建议按以下维度展开：

- 哪些字段为空值比例高
- 哪些字段已有值但格式不标准
- 哪些字段更适合先补
- 哪些字段应只补空值、不覆盖旧值

#### 2.2 执行方案

执行方案必须分两层写清楚：

##### A. API 

当前先拆成 `A. ScrapeCreators API` 与 `C. EasyKOL` 两层理解。

本节只定义 `A. ScrapeCreators API`。

脚本策略判断：

- 为了稳定使用 API 抓取，建议 `YouTube / TikTok / Instagram` 使用各自独立脚本
- 原因是 3 个平台的 endpoint、请求参数、payload 结构、可返回字段、覆盖规则都不同
- 通用 probe 脚本可以保留，但应只作为验证工具，不应长期承担生产回写
- API 层脚本统一放在 `scripts/api/`
- 浏览抓取层脚本统一放在 `scripts/browser/`
- 后续执行时，不再混用“看不出来源”的旧脚本名；优先使用分层后的入口名

当前推荐入口：

- `scripts/api/scrapecreators_probe.py`
- `scripts/api/youtube_scrapecreators_s1_apply.py`
- `scripts/browser/s1_browser_basic_enrichment.py`
- `scripts/easykol/s1_easykol_enrichment.py`

##### A.2 API 层当前建议

在当前状态下，`ScrapeCreators API` 不应被定义为稳定主流程，而应被定义为：

- 有额度且端点可用时的增强层
- 主要用于补 `联系方式 / 联系方式备注 / 粉丝数 / 简介 / 外链 / 类目`
- 生产实现上，优先采用 3 个平台独立脚本，而不是一个通用回写脚本硬兼容全部平台
- `粉丝数` 默认视为 API 直覆盖字段
- `语言 / 博主国家` 默认视为判断字段，不作为 API 直覆盖字段

##### C. EasyKOL 层

`EasyKOL` 在当前 `S1` 工作流里应被定义为联系方式增强层，而不是全字段补齐层。

适合补的字段：

- `联系方式`
- `联系方式备注`

不建议在 `EasyKOL` 层定义为可稳定补齐的字段：

- `账号ID`
- `频道/作者名称`
- `博主国家`
- `粉丝数`
- `语言`
- `账号简介__平台抓取`
- `账号类目标签__平台抓取`
- `外链__平台抓取`
- `近期10条均播`
- `置顶最高单条播放量 / 置顶最高播放`

当前建议：

- 把 `EasyKOL` 视为“Email 探测层”
- 命中 Email 时，回填 `联系方式`
- 同时在 `联系方式备注` 明确写入来源
- 若未命中 Email，不要幻想它还能稳定返回别的核心 S1 字段
- 若任务要求截图留证，优先使用 `scripts/easykol/s1_easykol_capture_panels.py`
- 当前截图推荐口径不是“固定百分比硬裁”，而是：
  1. 先打开新标签页进入目标主页
  2. 等 `EasyKOL` 面板异步注入完成
  3. 先定位右侧面板关键元素
  4. 尽量把面板居中到稳定区域
  5. 再裁 `panel` 与 `emailbox`
- 这样可以减少 YouTube 左侧留白、头图干扰、以及不同频道布局差异带来的裁切偏移问题
- OCR 只作为辅助，最终是否写回邮箱以截图里可清晰辨认的邮箱为准

#### 2.3 默认优先级建议

若用户没有额外指定，本工作流默认建议按以下优先级执行：

1. 先跑脚本 / 平台抓取层
   目标：补齐基础身份字段和平台原始事实
2. 再跑 API 层
   目标：补齐联系方式、粉丝数、简介、外链、类目等可增强字段
3. 最后跑 EasyKOL 层
   目标：只补 `联系方式 / 联系方式备注`

原因：

- 基础字段不完整时，直接跑 API / EasyKOL 层命中率更低
- 先把 `账号ID / 平台 / 链接 / 主页事实` 补干净，后续增强层更稳定
- `EasyKOL` 在当前定义下主要只承担 Email 探测，不适合放到前面承担主补齐职责

#### 2.4 默认批次规则

若用户只说处理人数、不额外指定批次大小，则默认按 `20` 条一批执行。

执行原则：

- `1-20` 条为 `Batch 1`
- 超过 `20` 条时自动拆分为多批顺序执行
- 每批都应先导出原始 JSON 到当天 `workbench/{YYYY-MM-DD}/`
- 每批都应先 `preview / review`，再决定是否 `apply`
- 每次正式写回前都必须按项目协议先备份主表

### Step 3. 执行补齐并回写

当且仅当目标表格与执行方案都已确认后，才进入正式执行。

建议执行顺序如下：

1. 先物理备份目标 `S1` 表
2. 先跑 `Dry-Run`
3. 再跑 `Test-Copy`
4. 最后才允许 `Write`

正式执行时，建议按以下顺序推进：

1. 先按平台拆分
   - `YouTube`
   - `TikTok`
   - `Instagram`
2. 再按字段层次拆分
   - 先跑脚本 / 平台抓取层
   - 再跑 API / EasyKOL 层
3. 再按范围拆分
   - 可先只处理缺失字段的行
   - 可先只处理 `Part1 / Part2`
   - 可先跑指定行号做验证

正式回写时必须遵守：

- 只补本轮确认的字段
- 若本轮定义为“只补空值”，则不得覆盖已有值
- `账号简介__平台抓取` 若要重抓，必须先清空旧值再写新值
- `联系方式备注` 必须写清来源，不写空泛备注

## 三、 异常与熔断处理 (Error Handling)

- 若用户未提供目标表格，必须先询问，不得自行假设
- 若表格并非 `S1` 表，必须先停下确认，不得误跑 `Raw` 或 `S2`
- 若字段分析尚未完成，不得直接启动脚本
- 若执行方案尚未获用户确认，不得进入正式写入
- 若 `平台` 无法识别，应先进入人工审查，不要强行路由
- 若 `账号链接` 缺失或明显异常，应先标记异常，不要直接跑 deep 层
- 若 `账号简介__平台抓取` 抓取不到有效内容，应保持空白，不得猜测
- 若 `联系方式` 找不到，统一留空；严禁编造邮箱
- 若脚本返回 404 或页面异常，可在备注类字段写入异常状态
- 若 deep 层命中率过低，应熔断并回到字段分析阶段，重新筛表后再跑

- 本轮执行方案
- 备份路径
- 脚本 / API 执行回执
