# S3 ReplyOps 升级方案

日期：2026-05-06

## 背景

`S3-ag-reply-draft-ops` 原始设计的前提是：agent 不能直接稳定读 Gmail 插件内容，所以必须更多依赖本地脚本恢复 thread、正文、附件与价格证据。

现在能力已经变化：

- agent 可以通过 Gmail 插件批量搜索 inbox
- agent 可以读取单封邮件正文
- agent 仍然没有插件原生“创建新 draft”的能力
- Rockbase 已有可验证的 Gmail OAuth token 草稿写入链路

因此升级目标不是替换 S3，而是把 S3 升级成混合架构。

## 升级目标

1. 用 Gmail 插件替代一部分“正文读取与筛选”工作
2. 用大模型直接阅读真实回复正文来判断意图、价格状态、下一步动作
3. 继续用本地 OAuth token 路线把 reply 写入 Gmail thread draft
4. 逐步接入 heartbeat / summary automation
5. 保留附件与 OCR 的 V3 证据层

## 对三个关键问题的结论

### 1. 插件能不能直接完成“读回复并写入草稿箱”？

不能完全靠插件闭环。

推荐正式路径：

- 读邮件：Gmail 插件
- 生成回复：大模型
- 写草稿：本地 OAuth token reply draft 脚本

一句话：

> 插件负责读，脚本负责写。

### 2. 能不能做成定时任务，并同步本地文档与云端文档？

可以。

建议拆成两层：

- 高频 heartbeat：定时查新回复、生成 draft、标记 manual review
- 低频 summary job：汇总当天回复、价格变化、已建 draft、待 review 项

建议落点：

- 本地：`workbench/{YYYY-MM-DD}/summary_replyops_daily_*.md`
- 实时状态：`.agent/NOW.md`
- 云端：Google Docs / Google Sheets

### 3. 附件怎么办？

附件仍然不能完全交给插件。

建议分流：

- 无附件：直接插件正文 -> 模型 -> 写 draft
- 有附件但不阻塞：先建 draft，标记附件存在
- 有附件且价格依赖附件：必须进入 `S3-ag-reply-recovery-sync-v3`

## 新旧能力分工

### Gmail 插件负责

- inbox 搜索
- unread 搜索
- thread 正文读取
- 小规模快速 triage

### `S3-ag-reply-recovery-sync-v3` 负责

- 回复 thread 长期恢复
- 附件下载
- OCR
- 价格证据层
- V3 主表结构化升级

### `S3-ag-reply-draft-ops` 负责

- 选择 template code
- 生成回复正文
- 创建 manifest
- thread 内 reply draft 创建
- draft / status 回写

## 当前最推荐的落地方式

不要立刻拆新 skill。

先在 `S3-ag-reply-draft-ops` 内部新增一组 plugin-first workflow：

- 最小验证 workflow
- 自动 triage workflow
- 自动 draft workflow
- 每日 summary workflow

等边界稳定后，再判断是否值得独立为新 skill。

## 2026-05-07 新增修正

经过第一轮 plugin-first draft sample，新增确认两条关键修正：

### 修正 1. 价格策略必须更强绑定模板

问题：

- 大模型虽然能读真实正文，但如果不强绑模板，很容易写出“礼貌但价格目标不明确”的回复。

结论：

- 生成 draft 时，必须以 `references/reply_templates.md` 作为唯一模板基准。
- 尤其是 `RQ1 / RI1 / RI2 / RI3`，价格相关动作必须在正文中显式出现，不能弱化成泛泛保温。

### 修正 2. Draft body 不能手工拼 quoted history

问题：

- 如果把对方原邮件和我方历史正文一起塞进新的 reply body，会让草稿变脏，也偏离正常邮件写作习惯。

结论：

- reply body 只保留新增加的回复内容。
- thread 关联应依赖 Gmail 的 `threadId / In-Reply-To / References`，而不是靠手工复制历史内容。

### 修正 3. 必须读完整 thread，而不是只看 latest message

问题：

- 只读最后一封，很容易忽略：
  - 已经出现过的价格追问
  - 已经谈过的 brief gate
  - 对方是在 follow-up 还是第一次报价

结论：

- plugin-first workflow 要升级成 thread-aware，而不是 latest-message-aware。
