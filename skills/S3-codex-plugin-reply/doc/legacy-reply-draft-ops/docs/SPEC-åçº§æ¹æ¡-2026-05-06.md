# S3 ReplyOps 升级方案

日期：2026-05-06
位置：`.agent/skills/S3-ag-reply-draft-ops/docs/SPEC-升级方案-2026-05-06.md`

## 1. 背景

S3 现有体系被拆成两个 skill：

- `S3-ag-reply-recovery-sync-v3`
- `S3-ag-reply-draft-ops`

原始设计前提是：当时 agent 不能直接稳定读取 Gmail 插件内容，因此必须依赖本地脚本完成 Gmail 抓取、thread 恢复、附件下载、OCR、价格抽取、主表回写，再进入 reply drafting。

现在情况已经变化：

- agent 已能通过 Gmail 插件直接批量搜索未读邮件、按 query 拉取邮件列表、按 message id 读取正文
- agent 仍然没有“插件原生创建新 draft”的能力
- 但 Rockbase 已经有一套经过验证的 Gmail OAuth token + manifest + sample/full + writeback 的本地脚本链路，已经可用于创建普通 draft 和 reply draft

因此，升级目标不应该是推翻 S3，而应该是：

1. 用 Gmail 插件替代一部分“邮件正文读取与筛选”工作
2. 保留本地 Gmail OAuth 草稿写入链路，作为 reply draft 的正式落点
3. 保留附件/OCR/recovery 的本地 Hub 能力，作为插件能力之外的证据层

一句话：

> 新 S3 应升级为“插件读内容 + 大模型判意图/写正文 + 本地 OAuth 写 reply draft + 自动汇总同步”的混合架构。

## 2. 这次升级要回答的三个问题

### 问题 1：既然现在能直接读 Gmail 内容，如何升级回复生成与草稿写入？

答案：

- 可以直接用 Gmail 插件批量查收件箱和回复线程内容
- 可以直接让大模型基于真实正文生成 reply body
- 但不能只靠 Gmail 插件完成“写入草稿箱”，因为当前插件没有 create draft 能力

因此，推荐方案是：

#### 方案 A：插件读，脚本写

流程：

1. Gmail 插件批量搜索待处理回复
2. Gmail 插件逐封读正文 / thread
3. 大模型结合你的北极星、模板规则、历史反馈，直接生成 `Mail2 / Mail3` reply body
4. 生成标准 reply manifest
5. 继续用 `create_reply_drafts_with_token.py` 这类本地 OAuth 脚本把 reply draft 写入 Gmail 原 thread
6. 回写 `Mail2_Draft_ID / Mail2_Status / Template_Code / Body_Final`

这是最稳的升级路径。

原因：

- 阅读能力交给插件，减少旧脚本在正文恢复上的误差
- 草稿创建仍交给已验证的 OAuth 路线，避免插件能力缺口
- 既保留 thread binding，又不丢失 manifest/resume/audit 体系

#### 方案 B：插件读，浏览器写

也可以用插件读邮件，再用浏览器自动化在 Gmail Web 里创建 reply draft。

但这条路不建议作为正式主路径，因为：

- 不如 OAuth API 稳定
- 容易受页面改版、弹窗、登录态影响
- 很难维持 manifest 级别的幂等和审计

#### 问题 1 的结论

正式升级方向应为：

- **读邮件**：优先 Gmail 插件
- **写草稿**：继续本地 OAuth token 脚本
- **正文生成**：优先大模型直接读取真实邮件内容，不再高度依赖旧“脚本预抽取结果”

### 问题 2：如何把它做成定时任务，并实时更新本地文档与云端文档？

答案：

这个能力可以升级成“双层定时”：

#### 层 1：Heartbeat / 定时巡检

用途：

- 每天固定时间或每隔一段时间查新的 inbox replies
- 把新增回复做分类
- 对适合自动回复的邮件生成 draft
- 对需要人工 review 的邮件做汇总

推荐动作：

1. 搜索新回复：例如 `in:inbox newer_than:1d` 或阶段性 query
2. 批量读取候选回复
3. 判定：
   - auto-draft-ready
   - manual-review
   - no-reply
4. 自动创建一批 reply drafts
5. 更新本地状态文档
6. 同步摘要到云端文档

#### 层 2：Daily Summary / 汇总同步

用途：

- 每日把新增回复、价格变化、已建草稿、待 review 项汇总成日报

推荐落点：

- 本地：
  - `workbench/{YYYY-MM-DD}/summary_replyops_daily_*.md`
  - `.agent/NOW.md` 中追加当前 live state
  - 必要时写 `workbench/handoff/`
- 云端：
  - Google Docs：写管理摘要
  - Google Sheets：写结构化回复流水、价格变化、reply stage

#### 为什么要双层

因为“自动建草稿”和“每日管理汇总”不是同一件事：

- 自动建草稿要高频、轻量、可续跑
- 日报要低频、汇总、适合人读

#### 问题 2 的结论

升级后的 S3 应支持两类自动化：

1. `reply intake heartbeat`
   - 查新邮件
   - 识别回复
   - 建 draft / 标 review
2. `daily reply summary heartbeat or cron`
   - 汇总当天回复
   - 更新本地 Markdown
   - 更新云端 Google Docs/Sheets

### 问题 3：附件问题怎么解决？

答案：

附件仍然不能只靠 Gmail 插件解决，至少当前不应这样假设。

原因：

- 你的报价信息经常在 PDF / image / media kit 里
- 插件的强项是搜索与正文读取，不是完整附件恢复 + OCR 审计
- 你原来的 V3 恰恰最有价值的部分，就是附件证据链

因此附件应采用“插件与本地 recovery 并存”的策略：

#### 正式建议

1. 正文和轻量 thread 判断：
   - Gmail 插件优先
2. 附件下载、OCR、价格证据抽取：
   - 保留 `S3-ag-reply-recovery-sync-v3` 本地 Hub 流程
3. 大模型最终价格判断：
   - 综合正文 + 附件证据

#### 升级后的附件策略

- 无附件：
  - 直接插件读正文 -> 大模型判断 -> 建 reply draft
- 有附件但正文已足够清楚：
  - 可先建 draft，同时把附件线程打上 `attachment_present_not_blocking`
- 有附件且价格判断依赖附件：
  - 必须进入 V3 attachment/OCR pipeline
  - 先抽证据，再决定模板或正文

#### 问题 3 的结论

附件不应该被“插件化替代”，而应该被“保留为 V3 的专业证据层”。

## 3. 升级后的目标架构

### 3.1 新架构原则

升级后 S3 应采用三段式：

1. **Inbox Read Layer**
   - Gmail 插件
   - 批量搜索
   - 批量读取目录
   - 按需逐封深读

2. **Intelligence Layer**
   - 大模型直接阅读真实邮件正文
   - 结合你定义的北极星、模板原则、报价策略、谈判偏好
   - 输出：
     - reply_intent
     - pricing_state
     - template_code
     - body_draft
     - manual_review_flag

3. **Execution Layer**
   - 本地 OAuth token reply draft scripts
   - manifest
   - sample/full
   - writeback
   - heartbeat / summary automation

### 3.2 新旧能力分工

#### Gmail 插件负责

- inbox 搜索
- unread 搜索
- thread 正文读取
- 轻量 triage
- 快速判读用户真实回复语气

#### Reply Recovery V3 负责

- 长期 Hub
- thread / attachment evidence 沉淀
- OCR
- 价格标准化
- replied master 结构化升级

#### Reply Draft Ops 负责

- 模板映射
- 回复正文生成
- manifest 建立
- thread 内 reply draft 创建
- draft 状态回写

## 4. 新 SOP 提案

### SOP A：轻量自动回复草稿流

适用于：

- 正文信息足够
- 不依赖附件
- 可以快速给出 `Mail2 / Mail3`

顺序：

1. Gmail 插件查新回复
2. 批量拉目录
3. 逐封读候选正文
4. 大模型根据北极星与模板系统生成 reply proposal
5. 标记：
   - auto-draft
   - manual-review
   - no-reply
6. 生成 manifest
7. 先 1 封 sample
8. 再 5 封 sample
9. 确认后批量写入 Gmail reply drafts
10. 更新本地主表 / review table / summary

### SOP B：附件驱动回复流

适用于：

- 对方发来 media kit / PDF / image
- 报价在附件里
- 正文不足以支持回复策略

顺序：

1. Gmail 插件发现回复并标记有附件
2. 线程进入 V3 attachment pipeline
3. 下载附件
4. OCR / 文本抽取
5. 构建 evidence pack
6. 大模型综合判断价格与 intent
7. 再进入 reply draft generation

### SOP C：每日摘要流

1. 汇总当日新增回复
2. 汇总当日已建 drafts
3. 汇总价格变化
4. 汇总 manual review cases
5. 写入本地 summary
6. 同步云端文档 / 表格

## 5. 对现有两个 skill 的升级建议

### 5.1 对 `S3-ag-reply-draft-ops`

应升级为：

- 增加“插件优先读取 Gmail 正文”的入口说明
- 保留 reply draft OAuth 写入脚本
- 增加“北极星 / operator feedback”驱动的 body generation 层
- 增加自动化入口说明
- 增加本地与云端 summary writeback 说明

建议新增模块：

- `docs/SPEC-升级方案-2026-05-06.md`
- `references/reply_northstar.md`
- `scripts/build_reply_review_queue_from_gmail_plugin.md` 或同类工作流说明
- `scripts/update_daily_reply_summary.py`

### 5.2 对 `S3-ag-reply-recovery-sync-v3`

应升级为：

- 明确自己是“附件与重型证据层”
- 不与插件正文读取竞争
- 在检测到附件相关风险时，被 `reply-draft-ops` 调用
- 输出更适合下游 draft generation 的标准字段

建议强化字段：

- `attachment_required_for_pricing`
- `auto_draft_ready`
- `template_code_suggestion`
- `template_confidence`
- `manual_review_reason`

## 6. 北极星定义建议

升级后如果要让 agent 更稳定地自动写回复，必须给一个更明确的北极星。

推荐北极星不是“把所有回复都回掉”，而是：

> 在不误发、不误判价格、不破坏商务姿态的前提下，尽可能自动生成高质量、线程绑定正确、可直接审阅的 reply drafts。

细化成四条：

1. 宁可少自动，不可错自动
2. 价格理解优先保守，不瞎补
3. 回复语气始终是 Rockbase 商务姿态
4. 自动化的目标是“给你省审阅成本”，不是“绕过你做最终判断”

## 7. 推荐实施顺序

### Phase 1

先升级 `S3-ag-reply-draft-ops` 文档与入口定义：

- 增加插件读正文 + OAuth 写 reply draft 的混合口径
- 明确 sample/full SOP

### Phase 2

加一个轻量自动化流程：

- 定时查新回复
- 生成 review queue
- 产出本地日报

### Phase 3

把附件线程接回 V3：

- 仅在有附件或价格不稳时触发重型 recovery

### Phase 4

再做云端同步：

- Google Docs 管理摘要
- Google Sheets 结构化回复流水

## 8. 最终结论

这次升级不应理解为“插件替代 S3”。

正确理解是：

- Gmail 插件替代一部分“读邮件正文”的旧工作
- 本地 OAuth 保留“写 reply draft”的正式链路
- V3 recovery 保留“附件/OCR/价格证据层”的核心价值
- 新系统升级为“插件读 + 模型判 + 脚本写 + 自动汇总”的混合 ReplyOps

这是最符合 Rockbase 当前实际能力、最稳、也最容易逐步落地的方向。
