# S1-S5 核心列讨论稿

## 目标

本文只回答第一个问题：

`S1 Inbox -> S2 Cold -> S3 ReplyOps -> S4 Hot -> S5 ClientReport`

在这条链路中，哪些列应该成为所有列表都共享的核心列。

这里的“核心列”定义为：

- 每个阶段都可能被读取
- 允许阶段内为空，但列本身必须存在
- 字段名和语义尽量保持一致
- 后续 workflow / skill 应优先围绕这组列做映射

## 讨论前提

当前锚点主表为：

- `Agency/list-master/【S4 Hot】KOL-Library.csv`

`S4 Hot` 应作为最终内部 Master 的骨架，但不是它的全部列都要强制下放到所有阶段。

原因：

- 有些列是结果列，不是过程列
- 有些列在早期阶段天然拿不到
- 若强制全表同构，会导致空列过多、维护成本上升

因此更合理的做法是：

- 所有阶段共享一组 `Core Columns`
- 每个阶段在核心列之外，增加自己的 `Stage-Specific Columns`
- `S4 Hot` 再承担汇总与沉淀角色

## 建议的核心列

我建议把核心列分成 4 组。

### A. 身份识别列

这些列决定“这个人是谁”，必须跨阶段稳定存在。

1. `账号ID`
2. `频道/作者名称`
3. `平台`
4. `多平台标记`
5. `账号链接`

保留理由：

- `账号ID` 是最重要的 merge key
- `频道/作者名称` 方便人工识别与质检
- `平台` 决定后续报价口径、内容形式和触达路径
- `多平台标记` 有助于后续识别 cross-post / bundle 场景
- `账号链接` 是人工复核入口

### B. 基础画像列

这些列定义“这个账号大概是什么样”，建议全阶段统一保留。

6. `语言`
7. `博主国家`
8. `粉丝数`
9. `账号类目标签`
10. `账号简介`
11. `粉丝受众`
12. `粉丝性别`
13. `粉丝年龄`

保留理由：

- 这些字段决定选号与客户匹配
- 它们虽然在 `S3` 不一定被主动更新，但应继续可见
- 后续从 `S1/S2` 流转到 `S4 Hot/S5` 时，这组信息不应该丢

### C. 商业判断列

这些列决定“值不值得合作”，属于全流程都常用的业务字段。

13. `置顶最高播放`
14. `近期10条均播`
15. `rate（USD$)报价`
16. `原价`

保留理由：

- `置顶最高播放` 可以帮助快速识别账号历史爆点与内容上限
- `近期10条均播` 是你当前业务里最关键的定价与判断变量之一
- `rate（USD$)报价` 是对外提案和内部筛选都绕不开的字段
- `原价` 对谈判、折扣、让利审计有长期价值

备注：

- 价格的上游结构可以更复杂
- 但每一阶段都至少应预留这两个主价格字段，保证数据能回汇到 `S4 Hot`

### D. 流转管理列

这些列帮助链路持续运转，也建议全阶段保留。

16. `提报备注`
17. `提报时间`
18. `提报人`
19. `备注`

保留理由：

- `提报备注` 更偏阶段入口说明
- `备注` 更偏自由补充与人工判断
- `提报时间` 和 `提报人` 便于审计和追溯

## 哪些 S4 Hot 列不一定要强制进所有阶段

如果目标是“降低管理难度”而不是“制造绝对整齐”，下面这些列可以视情况处理，不必强制所有阶段从 Day 1 就填满：

- `提报时间`
- `提报人`
- `原价`
- `粉丝受众`
- `粉丝性别`
- `粉丝年龄`

原因不是它们不重要，而是：

- 部分阶段拿不到
- 部分阶段不会更新
- 如果强制要求完整，会拖慢流程

因此建议：

- 这些列在结构上存在
- 但在流程上允许为空
- 后续由更靠后的阶段补齐

## 给 workflow 的启发

如果后续把这套逻辑变成 workflow 或 skill，建议规则是：

1. 所有输入表先映射到这组 `Core Columns`
2. 阶段专属字段单独保留，不污染核心列
3. `S4 Hot` 作为主汇总表，接受来自 `S1-S3` 的回填
4. `S5` 只从 `S4 Hot` 和必要的阶段专属字段中裁剪输出

## 当前建议

先不要追求 `S1-S5` 100% 同构。

- 同一套核心列贯穿 `S1-S5`

- `S4 Hot` 做唯一主库
- `S5` 做面向客户的裁剪视图
