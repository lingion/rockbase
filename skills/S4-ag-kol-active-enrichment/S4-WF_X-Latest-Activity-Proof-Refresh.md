# S4 Workflow: X Latest Activity Proof Refresh

## 目标

针对 X 表格中 `Latest Activity Proof` 已明显过时的账号，重新进入账号主页抓取最新活动，并更新以下两列：

- `Latest Activity Proof`
- `备注`

本 workflow 主要处理这类旧值：

- `2025`
- `2024`
- 更早年份
- 明显是旧 API 快照而非当前时间线结果

## 为什么要单独做

`Latest Activity Proof` 目前有一部分来自旧 API 源，存在明显过时的问题。

如果继续使用旧时间，会直接影响：

- 对达人是否仍活跃的判断
- 对触达优先级的判断
- 对客户交付时名单可信度的判断

所以这里必须回到 X 页面现场核验，而不是继续信任旧抓取源。

## 使用工具

- 优先使用 `omni-chrome`
- 使用已登录、已认证的 X 会话
- 不依赖匿名搜索结果替代主页核验

验证结论：

- 未登录状态下，X 首屏经常不是稳定的主时间线，容易出现旧卡片、混排卡片或不可信顺序
- 登录态是强制前提，没有登录就不要执行这条 workflow
- 若浏览器登录失效，应先恢复会话，再继续批处理

说明：

- `omni-chrome` 内已有认证信息，适合直接进入账号主页读取当前时间线
- 目标不是深抓历史内容，而是校验“最新一条活动”

## 适用范围

优先处理以下行：

- `Latest Activity Proof` 中年份为 `2025`
- `Latest Activity Proof` 中年份为 `2024`
- `Latest Activity Proof` 中年份更早
- `Latest Activity Proof` 为空，但账号仍可打开

不优先处理：

- 已明确 `404`
- 已明确 `protected`
- 已明确 `suspended`

这些情况应走异常状态规则。

## 核心原则

### 1. 回到页面真值

- 不信任旧 API 时间
- 直接看 X 当前主页时间线
- 只要页面可见，就以页面最新活动为准

### 2. 只抓最新一条

- 不做长链路回溯
- 不翻很多屏
- 目标只是拿到“当前最新活动证明”

### 3. 五个一组

- 每次处理 `5` 个账号
- 抓完这一组立即落盘
- 落盘成功后再进入下一组

这是强制规则，不要一口气积压很多未写入结果。

### 4. 页面优先，字段后判

先抓最新活动，再决定是否加 `活跃度低`。

不要先凭旧年份做结论。

### 5. 先排序再抓

- 对主表执行前，先把 `P1` 按 `Latest Activity Proof` 日期从新到旧重排
- 本 workflow 当前优先处理 `P1`
- 当前实操 cutoff 为 `2026-01-01`
- 每一轮只抓 `P1` 中 `Latest Activity Proof < 2026-01-01` 的前 `5` 个

## 执行流程

### Step 0: 预筛选

从目标 CSV 中筛出：

- `Latest Activity Proof` 含 `【2025-`
- `Latest Activity Proof` 含 `【2024-`
- `Latest Activity Proof` 含更早日期
- 当前正式脚本默认限定为 `P1`
- 且限定为 `Latest Activity Proof < 2026-01-01`

形成待处理队列。

### Step 1: 5 个一组载入

每组只取 `5` 行。

每行至少带上：

- `账号ID`
- `账号链接`
- 当前 `Latest Activity Proof`
- 当前 `备注`

### Step 2: 用 omni-chrome 打开 X 主页

优先顺序：

1. `账号链接`
2. 若链接缺失，则用 `https://x.com/{handle}`

进入账号主页后：

- 等待时间线加载
- 不依赖搜索页
- 不优先点外链
- 若 `goto` 超时，允许重试 `1` 次
- 仍失败则本轮跳过，不覆盖原值

### Step 3: 读取最新活动

优先读取账号时间线最上方的最新活动。

优先级：

1. 最新原创帖
2. 若没有原创帖，则可接受最新回复
3. 若前两者都没有，则可接受最新转发 / repost

注意：

- 尽量跳过置顶帖，如果置顶帖明显不是最新日期
- 以页面最新时间为准，不以置顶位置为准
- 若页面首屏就是最新活动，无需继续下滑
- 优先取主时间线里“首个非置顶可见活动”
- 若首屏没有拿到非置顶卡片，才允许轻微下滑一次再读
- 这一轮验证里，登录态下“首个非置顶可见活动”比按页面混排日期排序更稳定

### Step 4: 生成标准化 proof

统一写成：

- `【YYYY-MM-DD】Posted: ...`
- `【YYYY-MM-DD】Replied: ...`
- `【YYYY-MM-DD】Reposted: ...`

内容规则：

- 截取最新活动前 `80-120` 个字符左右
- 保留足够识别度
- 去掉明显多余换行
- 不必追求完整全文

示例：

- `【2026-03-19】Posted: This is the most challenging thing I've ever done as an entrepreneur. It is b...`
- `【2026-02-27】Replied: Strong take. The real unlock for agents is not raw capability, but workflow reliability...`

## 更新规则

### 情况 A: 浏览器结果比原 proof 更新

处理方式：

- 只有当浏览器抓到的日期 **晚于** 当前表内 `Latest Activity Proof` 日期时，才覆盖
- 若更新后的日期是 `2026`，`备注` 不新增 `活跃度低`
- 若原备注里已有 `活跃度低`，且最终 proof 已更新到 `2026`，应移除 `活跃度低`
- 若更新后的日期是 `2025` 或更早，仍追加 `活跃度低`

### 情况 B: 浏览器结果没有原 proof 新

处理方式：

- 保留当前表内原有 `Latest Activity Proof`
- 不用更旧或同日但更脏的浏览器内容去覆盖 API 值
- 若最终保留的 proof 日期是 `2025` 或更早，则保留或补充 `活跃度低`

说明：

- 当前浏览器提取器仍可能抓到更旧卡片，因此执行策略必须是“只增不降”
- 浏览器的职责是发现 **更新值**，不是无条件覆盖

### 情况 C: 页面异常

若遇到以下情况：

- `404`
- `This account doesn’t exist`
- `Account suspended`
- `These posts are protected`
- 页面始终无法加载时间线

处理方式：

- 不编造 `Latest Activity Proof`
- 若该行已经存在可用 `Latest Activity Proof`，不要把单次抓取失败写成脏备注
- 只有在 proof 本身为空时，才允许补充 `latest-proof-check-failed`
- 若确认 404，可转交 `P4 / 404` 工作流处理

## 备注写入规则

### 新增 `活跃度低`

若最新活动时间是 `2025` 或更早：

- 若 `备注` 为空，写 `活跃度低`
- 若 `备注` 已有内容，在末尾追加 ` | 活跃度低`

### 不重复写

若 `备注` 已包含 `活跃度低`：

- 不重复追加

### 不覆盖其他风险备注

保留已有备注，例如：

- `media/personal`
- `media/institution`
- `marketing`
- `404 | unresolved`

`活跃度低` 只作为补充标签追加。

## 落盘规则

### 强制 5 个一组落盘

每处理完 `5` 个账号：

1. 立即写回 CSV
2. 立即保存
3. 记录本组完成状态
4. 再开始下一组

不要等全部处理完再统一写回。

### 比较后再落盘

每条写回前都要先比较：

1. 原表中的 proof 日期
2. 浏览器抓到的 proof 日期

只有在浏览器日期更晚时，才允许覆盖原值。

### 成功后清理脏备注

- 成功拿到浏览器 proof 后，应清理旧的 `latest-proof-check-failed`
- 不要让瞬时失败标记长期留在正式主表里

### 每组都要可恢复

若中途浏览器报错、登录失效或页面崩溃：

- 已完成的 5 个必须已经落盘
- 下一轮从未完成的组重新开始

## 推荐脚本结构

建议脚本分成 4 段：

1. 读表并筛出旧年份行
2. 生成 `batch_size = 5` 队列
3. 调用 omni-chrome 逐个抓最新活动
4. 每批 5 个写回 CSV
5. 成功批次结束后继续下一批

## 已验证的当前脚本

- 正式脚本：`scripts/refresh_x_latest_activity_proof.py`
- 当前策略：
  - 只处理 `P1`
  - 只处理 `Latest Activity Proof < 2026-01-01`
  - 每次 `5` 个
  - 登录态执行
  - 跳过置顶
  - 只增不降
  - `2026` 自动移除 `活跃度低`

脚本不负责“猜最新内容”，脚本只负责：

- 排队
- 调用
- 标准化写入
- 批量落盘

## 质检规则

每批处理完后至少抽查：

- `1` 个更新到 `2026` 的账号
- `1` 个仍停留在 `2025` 的账号
- `1` 个异常页账号

检查点：

- 日期是否来自页面真值
- `Latest Activity Proof` 是否被正确覆盖
- `备注` 是否正确追加 `活跃度低`
- 是否误删原有备注

## X 平台特殊注意

- X 首屏可能有置顶帖，不要把置顶帖误判为最新活动
- X 也可能优先展示转发或回复，要区分 `Posted / Replied / Reposted`
- 某些账号首屏加载慢，必须确认时间线已出现真实时间标签
- 若账号明显是机构号，也照样按最新活动刷新，不因账号类型跳过

## 输出要求

更新后：

- `Latest Activity Proof` 必须是当前页面最新活动
- `备注` 必须和活跃状态规则一致
- 每 `5` 个完成一组即落盘

## 结束定义

当以下条件都满足时，本轮任务完成：

- 目标表中所有 `2025/2024/更早` 的 proof 已复核
- 每条已复核记录都被新 proof 覆盖
- `2025/更早` 的账号都已正确标记 `活跃度低`
- 中途异常账号已被单独备注而不是被跳过
