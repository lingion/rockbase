# 【SOP】KOL 甲方汇报产物（文本与视觉）输出规范

> **总目标**：将内部的达人筛选策略（Briefing & Strategy）转化为**面向甲方客户（Client-Facing）**且具备高专业度的高级汇报产物。包含**文案结构技巧**与**HTML静态视觉排版**两大部分。
> **适用场景**：在项目中期，向甲方首次或多轮提交 KOL Candidate List 时。

---

## 📝 Part One: 文本汇报撰写 SOP (Content & Strategy)

> **目标**：指导文字版汇报方案在不同媒介下的话术红线与结构编排。

### 🔴 核心红线与注意事项 (What NOT to Write)

内部战略往往包含我们自己的统筹考量，但在面向乙方面向甲方的输出中，**必须严格过滤以下内部信息**，确保所有的精力完全聚焦于“为什么这些人匹配贵公司的品牌与受众”。

1. **🚫 严禁提及任何内部数据库黑话**：绝对不能出现 `T0`、`T1`、`T2` 库、`Master 表` 等字眼。
2. **🚫 严禁提及统筹层面的具体数量约束**：绝对不能强调“要选出 30 个人”、“最后只选 2-3 个”。汇报的基调是“这些是我们精选出的最佳答案”。
3. **🚫 严禁提及任何预算与 ROI 计算**：绝对不能出现具体的预算金额（如 `$5,000`）、报价上限（如 `<$2,500`）、砍价策略或 ROI 测算。我们要卖的是价值，不是在解释我们是怎么抠预算的。
4. **🚫 严禁在汇报中加入拼凑型或边缘选项**：例如如果核心红线是欧美，就精炼表达为欧美，不要加入诸如澳大利亚、印度等作为资源拼凑的防御性地区（除非 Brief 指导要求）。

---

### 🟢 汇报结构撰写规范 (Output Framework)

为了适应甲方在不同场景下的阅读体验，汇报文档**必须一次性输出 3 个版本**。

### 📌 版本 A：标准排版版（详尽结构）
* **适用场景**：正式提交的文件头部，或正式的阶段性全盘汇报。
* **结构要求**：分为三个具体的小节，语言专业、逻辑严密。
  1. **匹配思路**：跳出泛泛的行业标签（如泛 AI），点明结合甲方产品核心能力（如专业知识管理/工作流提效）建立的方向。
  2. **筛选依据**：阐述平台选择的理由（如为何全面锁定 YouTube 做长视频深度演示），以及受众市场与场景承接能力的验证方式。
  3. **重点关注维度**：列出 2-3 个能够明确打动甲方的细分考察点（例如：创作者能否传达“Thought Leadership”价值），并说明我们如何审慎过滤了非工作流相关的泛资讯号（如偏重硬件测评或新闻播报）。

### 📌 版本 B：商务精简版（汇报快读）
* **适用场景**：正式的工作邮件正文（Email Body），方便甲方高管或忙碌的对接人 30 秒内读懂。
* **结构要求**：包含 3 个带序号的简短段落（加粗标题）。
  * 核心逻辑是：**定向圈选了谁 -> 圈选的市场标准是什么 -> 从场景/质量上是如何把关的。**

### 📌 版本 C：极简结构版（核心三点）
* **适用场景**：微信 (WeChat) / Slack 等即时聊天工具的日常同步。
* **结构要求**：采用 Emoji 符号（如 ✅）开头的项目符号，每条只有一句话核心结论。
  * 范例特征：`✅ 平台受众锁定...`、`✅ 内容场景深植...`、`✅ 噪音严格过滤...`

---

### ✍️ 汇报语气特征 (Tone & Voice)

- **去数字化的质感表达**：用“锁定核心英语市场”代替“xx占比”。用“聚焦办公效率的创作者”代替“命中 AI 标签的数据”。
- **专业且对等**：保持 Agency 作为专家的自信（Professional Consultant 视角），不要过度解释具体的执行琐事，重点展示我们深入理解了甲方的“产品哲学与受众心智”。
- **结论先行**：只汇报最终沉淀下来的匹配理念与筛选基准。
- **正向表达优先**：避免使用“没有继续……”“不是……而是……”这类先否定再转折的写法，优先直接陈述本轮聚焦方向、筛选重点与匹配价值。

---

## 🖼️ Part Two: 静态 HTML 视觉模版规范 (Visual UI Design)

> **目标**：在完成文字版策略输出后，为高净值/核心客户生成单页、免交互、可整页截图的静态 HTML 视觉报告，提升 Rockbase/Agency 的专业提案质感 (Agency Export)。

为了在每次输出时保证稳定、高端的排版，我们在生成 HTML 时需严格遵循以下**结构化 UI 设计与 CSS 排版准则**：

### 1. “重头部反白”视觉锚点设计 (Heavy Dark Header)
一份具备“份量感”的商业报告，其第一视觉落点应当在页头。
* **重色块渐变**：Header 区域抛弃传统的白色，使用从左上到右下的深色渐变底色（如深藏青 `Navy Gradient` 或深灰黑色），给阅读者施加视觉重量。
* **全局反白 (Negative Space)**：在 Header 内的所有文字及 Logo 采用全反白（纯白或高亮透亮颜色），与深色底色形成极强对比。
* **双品牌背书 (Co-branding)**：在 Header 顶部留出区域给 Agency 自身（如左侧放入 Rockbase 方块 Logo + 文本），在核心标题区放置甲方品牌名称（放大部分字体大小，并加粗）。
* **背景光晕 (Ambient Glow)**：为避免深重色系过于沉闷，可通过局部放射性渐变 (`radial-gradient`) 在 Header 边缘添加微弱的发光点缀。

### 2. 动态色彩适配机制 (Client-centric Coloring)
我们的 HTML 框架应保持“骨架固定，皮囊动态适配”的策略。配色不再做死，而是每次生成时**汲取甲方公司的主色调**（如：甲方的品牌色是橙色/蓝色/紫色）：
* **Primary Color (主高亮色)**：提取甲方品牌配色，用于：按钮/编号/左侧边框/背景小圆点。
* **Secondary / Header Color (重色基调)**：提取甲方的深色系（如果没有，则默认使用极深藏青/深黑），专用于 Header 和最重要的标题文字。
* **Body Background (极简灰底)**：网页大背景保持极浅的冷灰色（如 `#F1F5F9` 或浅奶油色），报告的主体内容区块 (Container) 填充纯白色且附加轻柔的弥散阴影，形成悬浮卡片感。

### 3. 排版留白与截图适配 (Screenshot-friendly Architecture)
HTML 的首要使用场景是“全屏截图并在社交软件中发送”，因此宽幅和段落必须被严格约束。
* **容器锁宽 (Fixed Container)**：使用居中的主体 Container，`max-width` 锁定在 `860px - 900px`。这是在 PC 屏幕上进行长截图时，文字大小与留白最舒适的视觉比例。
* **模块化序号 (Section Numerals)**：每个大段落前的标题需要带上高亮的数字编号区块（如 `01`, `02`，带微弱底色填充），代替无聊的黑体字标题。
* **内容卡片化 (Card Grid)**：不要输出大段连篇的文本。将“方向一”、“方向二”等散点内容用 `grid` 或 `flex` 容器装进带 1px 淡边框的浅色矩形卡片中。
* **Highlight Block (高亮提纯区块)**：核心结论列表使用左侧带粗边框（`border-left: 4px solid var(--primary)`）的高亮气泡框包围；针对项目符号，废弃默认的黑点（bull/disc），使用圆角包裹的“✓”或与主色系绑定的定制 icon 渲染。

### 4. 字体质感 (Typography)
* 引入非衬线现代西文字体（如 `Outfit`, `Inter` 或 `Roboto`）作为英文字母与数字的基础，渲染粗细分明的层级对比（Headers 用 800/900，正文用 400）。
* 中文默认 Fallback 到系统无衬线字体（PingFang SC / Noto Sans SC）。段落行高（`line-height`）必须维持在 `1.6 - 1.7` 左右，以降低甲方快速阅读大段文字的压迫感。
