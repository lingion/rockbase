## 1. 目标重述

本轮任务不是泛化清洗全表，而是聚焦 `【Master】2026Mar-KOL.csv` 里 `Part one` 的全部邮箱联系人，完成两件事：

1. 把表格补全成可用于 Agency 内部检索与甲方汇报的资料库。
2. 基于 `【Templates】Emails_Rockbase_Outreach_Strategy.md` 的 `Version 2`，为每位达人生成可直接发送的 `Email subject` 与 `Email content`。

本轮执行单位建议为 **每批 20-30 人**，每批完成抓取、校验、改写、回填、质检，不做半成品堆积。

## 2. 单次抓取的最小闭环

每打开一个账号链接，必须在同一轮探测里尽量一次性完成以下字段补全，避免重复进站：

1. **称呼名写入 D 列 `平台作者`**

   - 对 YouTube 来说，D 列的**第一信源**必须是首页头部可见的频道主体名，也就是头像右侧的大标题。
   - 目标不是机械抄噪音文本，而是拿到最接近频道主体的可识别名称。
   - `平台作者` 的提取优先级应为：
     1. 首页头部可见主体名
     2. 页面元信息中的频道标题
     3. 其余页面文本中的主体名线索
   - `fallback` **不是** `平台作者` 的第一来源，它只用于邮件开头称呼的兜底生成。
   - 这里必须使用 **fallback 机制**，而不是单一规则硬套所有账号：
     1. **真人名优先**：若能抓到明确像真人名的强证据，优先用于邮件称呼。
     2. **团队名回退**：若抓不到真人名，但频道明显像品牌、工作室、团队主体，则使用压缩后的 `Channel Name Team`。
     3. **频道主体回退**：若既不像真人，也不适合加 `Team`，则直接使用频道主体名。
     4. **最终保底**：仅在主体无法可靠识别时，才使用 `Hi there,`。
   - 真人名只接受强证据来源：`About` 页署名、简介中的自我介绍、官网作者页、外链作者页、明确邮箱署名。
   - 若进入团队称呼模式，必须先做压缩，去掉冗长描述尾巴，例如：
     - `911Studios - Shopping, Gadgets & Tech` -> `911Studios Team`
     - `Prime Technology HD` -> `Prime Technology Team`
   - 若频道主体本身明显是“真人名 + 频道后缀”的混合形式，可在强可读前提下只保留真人主体，例如：
     - `Ben Kimball Ai` -> `Ben Kimball`
     - `Craig Campbell SEO` -> `Craig Campbell`
   - D 列仍保留可识别主体，但邮件正文中的实际称呼应按上述 fallback 逻辑自动选用，不单独新增字段。
2. **Handle 写入 C 列 `账号ID`**

   - 标准格式必须是带 `@` 的绝对正确 handle。
   - 若原值错误或缺失，直接覆盖。
   - 对 YouTube 而言，**不能只信任 `channel/UC...` 这类旧式链接**，必须优先抓页面头部真实显示的 `@handle`。
   - 推荐提取优先级：
     1. 页面头像旁/频道头部可见的 `@handle`
     2. 页面顶部正文区域里出现的 `@handle`
     3. canonical / URL 中已经显式存在的 `@handle`
     4. 最后才允许用兜底逻辑
   - 只要页面里能看到真实 `@handle`，就必须以它为准，而不是继续沿用 `channel/UC...` 链接推断结果。
   - 也就是说，首页头部的可见 `@handle` 是 `账号ID` 的第一信源。
3. **账号链接写回 F 列 `账号链接`**

   - 一旦拿到真实 `@handle`，必须同步把 `账号链接` 统一改写成规范 URL。
   - YouTube 统一格式：
     `https://www.youtube.com/@handle`
   - 不再保留以下旧格式作为最终结果：
     - `https://www.youtube.com/channel/UC...`
     - `https://www.youtube.com/@handle/videos`
     - 其他带 `/videos`、`/featured` 的变体路径
   - 目标是让后续所有抓取、复查、邮件引用都直接基于稳定的 `@handle` 链接，而不是混杂旧结构。
4. **校验 H/I 列：国家与粉丝数**

   - `博主国家` 必须统一改成中文，例如 `美国`、`英国`、`印度`。
   - `粉丝数` 以主页最新公开值为准，但表格落地时统一标准化为 `K/M` 形式，例如 `81K`、`266K`、`2.8M`。
   - 即使页面原本显示完整数字，也统一转成近似 `K/M`，必要时保留 1 位小数。
   - 若页面未直接展示国家，则结合简介、邮箱域名、外链、自我介绍、语言环境做谨慎判定；拿不准则保留原值，不强猜。
5. **填写 O 列 `达人定位简介`**

   - 这不是原始 bio 的翻译，而是给 Agency/甲方看的 **工作画像**。
   - 长度控制在 **50-100 字以内**，以能支撑后续匹配判断为准。
   - 每条都必须是定制化描述，严禁回落成 `AI工具创作者`、`科技测评频道` 这类可批量复制的标签句。
   - 禁止使用固定句骨架反复改词，例如：
     - `该频道以...为主`
     - `表达方式偏...`
     - `受众偏...`
       这类结构只能偶尔出现，不能成为整批默认模板。
   - 必须尽量写出 4 类信息：
     - 频道主要覆盖什么题材
     - 内容表达方式更像教程、测评、盘点还是热点解读
     - 近期选题的具体重心
     - 更适合哪类产品或哪类受众
   - 目标不是“归类”，而是让 Steve 后续一眼判断这个博主能不能接某个甲方 brief。
6. **抓取内容锚点素材**

   - 至少抓取最近 3 条内容标题。
   - 若平台可见播放/热度，先判断其中最值得引用的 1 条内容，再把它**压缩成主题短语**写入 W 列 `Email_Hook`。
   - `Email_Hook` 不再直接抄完整标题，而是写成更像真人会使用的内容概括，例如 `AI video workflows`、`consumer tech reviews`、`AI voice and dubbing tools`。
   - 若标题信息很弱，可补抓视频封面文案、频道栏目命名或简介关键词作为辅助锚点。
   - 最近 3 条标题不单独建列，直接整理后写入 N 列 `账号简介` 的前部，并与原始简介之间用分隔线隔开，方便后续人工连续浏览。

## 3. 关于“最近三条标题”的优化建议

结论：**可行，但不能只停留在机械抓 3 条标题。**

更优方案是直接落到现有列里：

1. N 列 `账号简介` 前部插入最近 3 条标题

   - 作用：保留原始素材，便于后续人工复核。
   - 格式建议：三条标题用 `|` 拼接，并在其后加入分隔线，再接原始简介。
2. W 列 `Email_Hook`

   - 作用：从三条标题里筛出最适合写进邮件的一条内容切口，并压缩成短主题。
   - 选择标准：
     - 与 AI / 效率 / 软件 / 工具评测更相关
     - 能在不引用原始长标题的情况下概括内容方向
     - 能体现其频道风格，而不是纯热点蹭流

原因很简单：
邮件里真正需要的是 **一个自然的切入点**，不是把三条标题硬塞进去。三条标题应该作为素材池，而最终正文只使用压缩后的主题短语。

## 4. O 列 `达人定位简介` 的生成逻辑

该列必须解决两个问题：`原简介太长` 和 `原简介不完整/缺失`。

### A. 当原始 `账号简介` 充足时

处理逻辑：

1. 先抽取账号核心主题。
2. 再判断内容形态：测评 / 教程 / 新闻 / 效率 / 创业 / 开箱 / 工具盘点。
3. 再结合最近 3 条标题，补出“近期选题在打什么方向”。
4. 最后转写成 Agency 视角的中文工作画像。

输出原则：

- 不写空话，不直接翻译原文。
- 不写“热爱科技”“分享生活”这种低信息量表达。
- 不允许整批重复同一套句式，必须带出该账号自身的题材差异。
- 优先写成“商业判断句”，而不是“类目标签句”。
  例如优先写：
  `主打 AI 视频生成与自动化内容，擅长把复杂工具拆成可复制流程，适合创作者工具合作。`
  而不是：
  `该频道以 AI 工具内容为主，表达方式偏教程拆解。`
- 尽量补出商业合作判断，例如受众偏科技消费者、AI 从业者、效率用户、电商卖家等。
- 文风要像 Agency 内部汇报，而不是像标签分类器。

### B. 当原始 `账号简介` 不完整或为空时

补全优先级：

1. 主页频道标题/副标题
2. 最近 3 条标题的共性主题
3. 外链首页一句话介绍
4. 视频栏目名称或置顶内容

也就是说，即使没有 bio，仍然可以通过内容主题反推出一个可靠的工作画像。
我们需要的不是“官方自我介绍”，而是 **对甲方有用的达人定位判断**。

### C. 已验证的问题根因与修正思路

这一列之所以容易写得机械，不是单纯模型能力问题，更核心的是**生成方法**是否把内容写成“分类标签”，还是写成“商业判断”。

已验证的主要问题：

1. **固定句骨架重复**

   - 如果默认总是写成：
     - `该频道以...为主`
     - `表达方式偏...`
     - `受众偏...`
   - 那即使换词，也会整批看起来像模板改写。
2. **关键词过宽，容易误判题材**

   - 例如把 `review`、`video`、`audio` 这类泛词直接当成强分类信号，就会出现：
     - 消费科技频道被误判成 AI 视频频道
     - AI app review 频道被误判成数码硬件频道
     - 商务邮箱、合作说明把频道误判成“副业变现”方向
3. **把联系方式噪音混进了题材判断**

   - `business@...`
   - `collab@...`
   - `For promotion`
   - `Telegram / WhatsApp / 微信`
   - 这些文本如果不先剥离，会干扰频道真实定位。
4. **写成了类目归档，而不是投放判断**

   - 好的 `达人定位简介` 不该只是“你属于什么类目”，而应该回答：
     - 你主要讲什么
     - 你怎么讲
     - 你最擅长把什么讲清楚
     - 你适合接什么样的产品

修正原则：

1. **先去噪，再判断**

   - 在生成 `达人定位简介` 前，必须先剥离：
     - 邮箱
     - 外链
     - 商务合作说明
     - Telegram / WhatsApp / 微信等联系信息
   - 这些内容只用于联系方式字段，不参与频道画像分类。
2. **用“题材簇”判断，不用单个泛词硬判**

   - 例如：
     - `Kling / Seedance / Higgsfield / Sora / cinematic / filmmaking`
       才更适合归入 `AI 视频生成与影像工作流`
     - `iPhone / iPad / Mac / Samsung / unboxing / charger / hardware`
       才更适合归入 `消费电子、系统更新与数码硬件`
   - `review`、`video` 这类泛词只能辅助，不能单独决定频道定位。
3. **优先输出“商业画像句”**

   - 优先写：
     - `频道聚焦 AI 自动化与工作流内容，擅长把复杂工具拆成真实业务可执行的流程，适合智能体和效率工具合作。`
   - 而不是：
     - `该频道以 AI 工具内容为主，表达方式偏教程拆解。`
4. **每条至少要有 3 层信息**

   - `核心题材`
   - `内容表达方式`
   - `商业适配判断`
   - 最好再补一层：
     - `独特价值 / 擅长点`
5. **允许保留空值，不强行幻觉**

   - 如果简介、标题、主页信息都不足以支撑稳定判断：
     - 可以写成保守画像
     - 或进入“待人工复核”状态
   - 不允许为了“每行都写满”而编造频道定位。

本轮已经验证有效的优化方向：

- 先剥离联系方式噪音，再做题材判断
- 收紧关键词优先级，避免 `review / video` 这类泛词带偏频道画像
- 把 `达人定位简介` 改写成“核心内容 + 表达方式 + 独特价值 + 商业适配”的画像句
- 禁止整批默认复用 `该频道以...为主 / 受众偏...` 这种标签骨架

## 6. 邮件生成原则（基于 Version 2）

`Version 2` 可以继续作为主模板，但要标准化成“半固定 + 半定制”的生成结构。

### 固定部分

- Rockbase Agency 身份背书
- AI 品牌合作经验
- Q2 creator shortlist 的商务表述
- 询价 CTA
- 署名

### 定制部分

- `Greeting_Name`：来自 D 列与 fallback 机制，且写入 X 列时必须是**完整称呼句**，例如 `Hi Craig,`、`Hi AI Boss Team,`
- `Platform_Author`：频道/账号主体名
- `Email_Subject`：后续回填时不再写成长标题，不直接塞完整视频名；采用“短标题骨架 + 受众短语”结构
- `W 列 Email_Hook`：用于正文首段，只放压缩后的主题短语，不直接复读视频完整标题
- `Specific_Detail`：不要求过深内容理解，可写成对其选题方式、拆解方式、测评角度的轻量观察
- `Topic_Tag`：来自 O 列 `达人定位简介` 和最近内容主题
  这里不能只做宽泛提取，必须和 O 列里的真实频道画像一致。

### 关键约束

1. 个性化内容要显得“看过内容”，但不能写得像深度粉丝。
2. 标题必须足够短，优先提高打开率，不把完整标题复制进 Subject。
3. 正文首段不要机械粘贴完整视频标题，而要把内容压缩成主题短语后再写。
4. 不强行吹捧，不写空泛赞美。
5. 若素材不足，宁可简化定制段，也不要编造具体视频细节。

4. F 列 `账号链接` 是否已统一改写为 `https://www.youtube.com/@handle`
5. 国家是否已中文化
6. 称呼是否遵守 fallback 机制，而不是无证据硬猜人名
7. O 列 `达人定位简介` 是否真的在 50-100 字区间内
8. O 列 `达人定位简介` 是否真的具备差异化，而不是批量复读同一类模板句
9. 邮件内容是否引用了正确标题
10. 是否出现编造细节
11. X 列 `Greeting_Name` 是否已经是完整称呼句，而不是裸名字或脏数据
12. 若 Y / Z / AA 暂空，是否属于当前策略允许范围，而不是漏写

## 8. 执行判断标准

如果一位博主最终满足以下条件，则视为可投递：

1. 有可用邮箱
2. 有稳定称呼方式
3. 有可靠定位简介
4. 有至少一个可写入邮件的内容锚点
5. 至少已具备稳定称呼与可用内容锚点；Y / Z / AA 可后置生成

如果不满足，则该行标记为待人工复核，而不是硬生成低质量邮件。
